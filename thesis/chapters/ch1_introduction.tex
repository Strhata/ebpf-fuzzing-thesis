\section{Motivation}
\label{sec:motivation}
% --------------------------------------------------------------------------

The extended Berkeley Packet Filter (eBPF) has become one of the most consequential
infrastructure technologies in modern Linux systems.
Originally a packet-filtering mechanism, eBPF has evolved into a general-purpose
kernel extension framework that allows user-supplied programs to run inside the
kernel with near-native performance, without requiring kernel modules or source
modifications.
Production deployments span a wide range of use cases: Cilium uses eBPF for
high-performance Kubernetes networking; Falco and Tetragon use it for runtime
security monitoring; XDP (eXpress Data Path) uses it for line-rate packet
processing; bpftrace and the Linux perf subsystem use it for low-overhead
kernel observability.

Central to this framework is the \emph{verifier}: a static analysis engine of
approximately 21,000 lines of C code that checks every eBPF program before it is
allowed to execute.
The verifier traverses all possible execution paths through the program's control
flow graph, tracking the type of every register at every program point and
enforcing memory-safety, type-safety, and termination constraints.
Only programs that pass this analysis are JIT-compiled and executed at kernel
privilege.
The verifier is therefore the primary --- and in many deployment configurations the
only --- barrier between user-supplied code and the full power of the kernel.

Logical flaws in the verifier have real consequences.
CVE-2023-2163 exploited a flaw in the verifier's state-pruning logic, which
incorrectly marked unsafe code paths as equivalent to already-verified safe ones,
enabling an unprivileged user to read and write arbitrary kernel memory.
CVE-2024-41003 exploited a flaw in the handling of certain instruction sequences
to achieve a similar effect.
A recent systematic study of eBPF security reported over 100 verifier-related
security issues in 2024 alone~\cite{sok-ebpf}.
Because eBPF programs are loaded via ordinary system calls that are accessible to
unprivileged users on stock Linux kernels and in many containerised and CI
environments where the restriction is relaxed, each such vulnerability
represents a potential path from a nominally sandboxed process --- a container,
a package script, a CI agent --- to full kernel code execution.
Systematically testing the verifier for such flaws is therefore a high-priority
security research goal.

Coverage-guided fuzzing is the most effective automated technique for finding logic
bugs in complex software~\cite{afl,syzkaller}.
Applied to the BPF verifier, the approach would: generate BPF programs, submit
them via the \texttt{BPF\_PROG\_LOAD} syscall, instrument which kernel code paths
are executed, and use that feedback to steer generation toward less-explored paths.
The fundamental challenge is \emph{structural validity}.
Most random byte sequences fail basic encoding checks --- invalid opcode byte,
misaligned instruction boundary, unresolvable jump target --- before the verifier
executes any interesting analysis logic.
Random mutation is therefore highly inefficient: the fuzzer spends almost all of
its budget generating programs that are discarded before reaching the code under
test.

\section{Problem Statement}
\label{sec:problem}
% --------------------------------------------------------------------------

Existing eBPF fuzzers address the structural-validity problem through hand-crafted
generation rules.
Buzzer~\cite{buzzer}, an open-source eBPF fuzzer from Google, implements two
fixed Go strategies: \texttt{pointer\_arithmetic} and \texttt{coverage\_based}.
BRF~\cite{brf} uses a constraint-based generator to produce type-correct programs.
Neither employs a learned model of BPF program structure.

On the LLM side, recent work has demonstrated that language models can generate
syntactically valid inputs for fuzzing JavaScript engines~\cite{covrl}, general
C programs~\cite{fuzz4all}, and syscall interface specifications~\cite{kernelgpt}.
None of these systems targets BPF bytecode generation, and none uses live kernel
coverage instrumentation as an RL reward signal.

This identifies a genuine and previously unfilled gap: \textit{no existing system
combines LLM-guided eBPF program generation with live KCOV kernel PC coverage as
a reinforcement-learning feedback signal for the BPF verifier.}
This thesis builds such a system. Buzzer serves as its inspiration and as the
source of training data; the contribution is the learned, coverage-rewarded
generator that no prior work provides.

\section{Contributions}
\label{sec:contributions}
% --------------------------------------------------------------------------

This thesis makes the following three contributions:

\begin{enumerate}

  \item \textbf{An end-to-end LLM-driven fuzzing system.}
        We design and implement a complete pipeline for LLM-guided eBPF verifier
        fuzzing: a modified buzzer instance dumps BPF programs and verifier outcomes
        as JSONL at the kernel FFI boundary; a QLoRA fine-tuning stage trains a
        language model on the resulting dataset; a GRPO RL stage uses KCOV kernel
        PC coverage as the reward signal; and a Go binary running inside a
        KCOV-instrumented Linux~6.8 VM validates each generated program and
        returns its coverage trace. The central engineering obstacle --- bridging
        LLM text to raw BPF bytecode without a clang dependency --- is solved by a
        pure-Python encoder. The stages are independently replaceable, making the
        pipeline reusable by swapping the SFT data or the reward function.

  \item \textbf{The diversity wall: a characterized negative result.}
        On the metric that matters --- unique KCOV PCs reached by \emph{valid}
        programs --- fine-tuning solves validity but not exploration. The model
        progresses from trivial one-instruction programs to deep, valid ones, yet
        their coverage \emph{saturates}: increasing the number of valid programs by
        more than an order of magnitude reaches only marginally more verifier paths,
        because the generator collapses onto a narrow mode of similar programs.
        We show this collapse originates at the supervised stage and quantify it.
        \emph{Diversity, not validity, is the wall.}

  \item \textbf{GRPO gradient starvation: diagnosis and a structural fix.}
        We run a GRPO loop (run~1, 8{,}370 steps) and observe a training collapse:
        the within-group reward standard deviation falls to zero in 99.5\% of
        batches, zeroing the gradient~\cite{grpo-starvation}. We trace the cause to a
        homogeneous reward and fix it with a \emph{validity-gated soft-floor}
        reward, which grants rejected programs graded partial credit --- guaranteeing
        non-zero within-group variance by construction --- while keeping accepted
        programs strictly higher, so the policy is still driven toward validity. A
        second run confirms the starvation does not recur.

\end{enumerate}

\section{Thesis Structure}
\label{sec:structure}
% --------------------------------------------------------------------------

Chapter~\ref{ch:background} provides the background necessary to follow the rest
of the thesis: eBPF architecture and verifier operation, KCOV kernel coverage
instrumentation, coverage-guided fuzzing, LLM supervised fine-tuning and
parameter-efficient adaptation, and the GRPO policy-gradient algorithm.
Chapter~\ref{ch:related-work} surveys prior work in three clusters: eBPF-specific
fuzzers, LLM-based fuzzing systems, and reinforcement learning for code generation.
Chapter~\ref{ch:methodology} describes the research methodology: the data
collection strategy using buzzer, the SFT pipeline design including the assembly
format decision, and the design and redesign of the RL reward function.
Chapter~\ref{ch:implementation} details the implementation of the four main
components: the pure-Python BPF encoder, the \texttt{kcov\_validator} Go binary,
the GRPO training loop, and the remote reward pipeline for cloud-based training.
Chapter~\ref{ch:results} presents the experimental results as the sequence of runs
that produced them --- SFT-1, RL run~1's gradient starvation, the reward and format
redesign, SFT-2, and RL run~2 --- and characterizes the diversity wall that is the
central finding.
Chapter~\ref{ch:conclusions} draws conclusions from the work, summarises the
lessons learned about the pipeline and about GRPO reward design, and enumerates
concrete directions for future work.
